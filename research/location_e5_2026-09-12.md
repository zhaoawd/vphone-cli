## 真实控制入口结果

| 场景 | 实验设置与结果 |
| --- | --- |
| 固定位置与客户端消失 | 固定坐标 31.2/121.5，heartbeat 0.2 秒；每次请求后关闭客户端连接，宿主仍继续递增 delivery sequence |
| 持久化写入与清除 | `persist:true` 创建实例内 `system-location.json`；替换为流、停止或 GUI 切换后删除文件 |
| owner 与 generation | 不同 owner 无 replace 返回 `location_owner_conflict`；显式替换生成新 generation；旧 generation 的 push/stop 返回 `location_generation_conflict` |
| producer sequence | 首次必须为 0；相同序号与相同内容重试不重复交付；同序号改内容或跳号返回 `location_sequence_conflict`；下一连续序号可交付 |
| 暂停与恢复 | 暂停状态为 paused，speed 为 0；暂停期间可接收下一样本并保持 paused；恢复后为 running；停止后 generation 为空 |
| 超时 hold | watchdog 0.4 秒；生产者停止推送后为 holding、speed 为 0；后续连续序号推送恢复 running |
| 超时 stop | watchdog 0.4 秒；停止推送后 state 为 off，generation 为空 |
| GUI 与外部源切换 | GUI 选择 Sync Host Location 后外部 owner/generation 和持久文件清除；随后外部固定源可以取得所有权 |
| 客户机重连 | 保留 GUI 同步开关开启状态，再设置外部固定源；终止经路径核对的客户机守护进程，3 秒后按原部署方式重新启动。7.408 秒内观察到断线、重连及固定源恢复；generation、owner、坐标保持一致 |

最后一项包含人为设置的 3 秒停机等待和轮询开销，不是纯重连性能指标。该实例由 autophone 直接启动缓存守护进程，因此此处验证的是服务重新可用后的宿主重连与定位恢复，不宣称 launchd 自动重启已验证。

## 环境问题与处理

1. rig2 启动测试中，宿主程序在创建 VM 前退出，`--help` 最小复现也返回 -9。E4 app 静态签名校验通过，新建 E5 app 的 `make build` 成功但仍返回 -9。AMFI 日志明确记录 Code=-424：`The file is adhoc signed but contains restricted entitlements`。这是本轮新进程启动失败的已确认原因，不能用于解释历史客户机握手超时。
2. 原 VM 初始客户机没有 `location_owned`。首次缓存更新后终止守护进程，服务没有自动重启。随后检查发现 autophone 的 `vphoned_fix.sh` 会移除原 launchd 服务并直接启动缓存程序；现场也没有对应 launchd job。通过既有 mobile SSH 和 sudo 恢复旧缓存并直接启动后，Shell 恢复。
3. 第二次更新采用临时文件加 rename，同时临时同步宿主用于自动更新的 `.vphoned.signed`，避免重连覆盖回旧版本。按原方式直接启动后，客户机声明 `location_owned`，上述定位场景通过。没有修改固件或原宿主应用程序。

项目已有 `scripts/start_amfidont_for_vphone.sh` 可恢复项目路径的签名放行进程，但会改变宿主签名校验行为；本轮已就这个具体动作请求授权，尚未执行。C4 继续暂停，没有复制 VM 磁盘或创建大型固件。

## 自动化测试

完整 `make test` 在新增测试前退出码为 0：85 个 Python、127 个 XCTest（3 个跳过）通过；Swift Testing 快速套件也通过。新增测试后的定位专项共 65 个 XCTest，通过：

- 原持久化恢复测试增加原 generation 与恢复 generation 的不相等断言。
- 一个实例的截断 JSON 被隔离保存，另一个实例的持久文件、generation 和已交付位置保持不变。
- 持久固定源被流替换后，重新加载状态存储保持 off，不恢复旧固定源或流。

这些测试使用真实状态文件和控制器、替身客户机；不替代宿主进程重启或两个真实 VM 的隔离验收。生产定位代码没有修改，没有新增二进制补丁。
